# dsh-task-brief

DeepSeek Harness 插件：每个新会话的第一条任务，先给一份《任务简报》再开工。

它解决的是一个很具体的问题——新会话刚开始时，你不知道这次任务要花多少资源、该用哪个模型。插件把这段判断前置：模型在动第一个工具之前，先把任务、类型、难度、硬性要求、工作量、Token 与时间估算、推荐的模型与思考等级，一次性摊在桌面上。

**只建议，不自动切换。** 插件不会改动你的模型选择。

## 效果

新会话发第一条任务后，回复开头会是一张这样的表：

| 项目 | 内容 |
|---|---|
| 任务 | 把 v1 的登录接口迁到 v2 网关，并补 5 条回归测试 |
| 类型 | 代码实现 / 重构 |
| 难度 | ★★★☆☆ —— 接口语义有差异，回归用例要覆盖旧行为 |
| 关键要求 | 不改动 v1 接口；测试必须能在 CI 单跑；不引入新依赖 |
| 工作量 | 约 8 个文件改动，20–30 次工具调用，需要读现有实现 |
| Token 估算 | 输入 ≈ 70k、输出 ≈ 15k、合计 ≈ 85k（估算） |
| 时间估算 | 15–25 分钟 |
| 推荐配置 | `xdpool/deepseek-v4.1-flash · 思考等级: high` |
| 推荐理由 | 多文件按规格执行，不需要跨模块架构推理；max 的额外收益有限 |

> 按推荐继续

表格之后直接开工，不再等一次确认。

只有一句话就能答完的寒暄、纯问答或澄清反问会跳过简报，避免变成噪音。

## 触发规则

- **什么时候有**：新会话的第一轮任务。
- **什么时候没有**：会话已经完成过至少一轮对话（包括续接的历史会话、带历史的 fork），以及本轮的实质只是寒暄或反问。
- **空白新会话**还会在输入框右上角显示一枚「首轮先出任务简报」的小提示，让你在发任务之前就知道会拿到什么。

## 它怎么知道该推荐哪个模型

插件在 Host 侧向 `ctx.llm` 取一次**本次运行的真实目录**（哪些 provider、哪些模型、各自支持哪些思考等级、上下文窗口多大），连同当前会话的默认模型和思考等级，一起注入到这个 Agent 自己作用域的系统提示里。所以你看到的推荐只会在你实际能选的组合里出现，不会凭空发明模型名。

目录会随 `llm/adapters-updated` / `llm/models-updated` 事件刷新，换 provider、加模型后无需重启。

## 安装

本地目录安装（开发/自用）：

```bash
# 在 DSH Web 界面：Plugins → Add plugin → 选择本目录
```

或从 npm 安装（发布后）：

```
Plugins → Add plugin → dsh-task-brief
```

安装后在新会话里验证：发一条真实任务，回复开头应当出现 `## 任务简报` 表格。

## 配置

插件行 `task-brief` 的 `config`，写在 profile 的 `cordis.patch.yml`：

```yaml
- id: task-brief
  name: 'dsh-task-brief'
  config:
    enabled: true            # 总开关
    includeModelCatalog: true # 是否把实时模型目录注入提示词
    maxCatalogModels: 24     # 最多列多少个模型
    catalogTimeoutMs: 12000  # 取目录的超时；超时则按通用能力推荐
```

## 边界与代价

- 简报本身是一次额外的输出，通常 200–400 token。不想要时可以关掉 `includeModelCatalog` 省一点输入。
- 估算都是**量级参考**，不是实测。插件只会给区间并标注为估算；如果你的模型把它写成精确数字，那是模型的问题，不是插件承诺。
- 只注入提示词，不写 Session 日志、不新增事件类型、不改你的模型选择，因此对续接、fork、回放都是安全的。
- 关掉插件后，新会话的简报与提示条同时消失，历史会话不受影响。
